## 0-1. 운영자 작업 — 제공자별로 묶음 (제한적 베타까지, 이 순서)

같은 서비스에 두 번 들어가지 않도록 제공자별로 묶었습니다. 자세한 설명은 각 번호의 본문을 보세요. **값(비밀키·비밀번호)은 어디에도 붙여 넣지 마세요.**

### A. Supabase — 쿠폰 발급 안전 함수 설치 (베타 필수, 약 10분)
- **접속**: Supabase Dashboard → 운영 프로젝트 → **SQL Editor** → `New query` (매번 **새 탭**)
- **순서**
  1. 새 탭에 `db/verify/pre-apply-check.sql` 전체를 붙여넣고 Run → `ord` 10~90이 **모두 `ok = true`**
  2. 새 탭에 `db/migrations/20261012_issue_coupon_atomic.sql` **파일 하나만** 붙여넣고 Run → `Success. No rows returned`
  3. 새 탭에 `db/verify/post-apply-check.sql`을 Run → `ord` 10~16이 모두 true (20번대는 포인트 SQL을 적용하지 않았으므로 false가 정상)
  4. 새 탭에 아래를 Run → 결과가 `{"status": "user_not_found"}` (아무것도 기록되지 않음)
     ```sql
     select public.issue_coupon('00000000-0000-0000-0000-000000000000'::uuid, '00000000-0000-0000-0000-000000000000'::uuid, '0');
     ```
- **성공 확인**: 위 3·4번 + 이후 Sentry에 `issue_coupon() is missing` 이슈가 새로 생기지 않음
- **중단 조건**: 1번에서 `false`가 하나라도 있음 / 2번에서 오류 문구가 나옴 / 3번의 10~16행 중 `false` / 4번 결과가 다름 → **멈추고** 해당 결과를 전달. 이미 적용했다면 복구: `drop function if exists public.issue_coupon(uuid, uuid, text);` (그러면 수량 제한 쿠폰만 다시 "발급 불가"로 막히고 나머지는 정상)
- **포인트 SQL(`20261012_point_use.sql`)은 이번 베타에 필요 없습니다.** 포인트 "사용"은 꺼져 있고(적립만 동작) 사용처 정책도 없습니다. 사용처가 확정되어 기능을 켤 때 5번 절차로 적용하세요 — 그 전에 적용하면 아무 이점 없이 DB 표면만 늘어납니다.

### B. Resend + 도메인 DNS — 일반 이용자에게 메일이 가게 하기 (베타 필수)
- **접속**: ① 도메인을 산 곳(가비아/Cloudflare 등)의 DNS 관리 ② Resend Dashboard
- **순서**: Resend → **Domains** → `Add Domain`(발신에 쓸 도메인, 예: `mail.<서비스 도메인>`) → Resend가 **화면에 보여주는** SPF/DKIM(필요 시 DMARC) 레코드를 **그 값 그대로** DNS에 추가 → Resend에서 `Verify`
- **성공 확인**: Resend의 도메인 상태가 **Verified**
- **중단 조건**: 며칠이 지나도 Pending/Failed → DNS 레코드 오타·중복·이름 형식(호스트 부분)을 Resend 안내와 대조. 도메인이 아직 없다면 3번(도메인 전환)이 먼저입니다. 이 값은 제가 만들어 드릴 수 없습니다(Resend가 계정마다 다르게 발급).

### C. Vercel — 메일 발신 주소 설정 + 재배포 + 확인
- **접속**: Vercel → Project `japan-coupon` → Settings → **Environment Variables**
- **입력**: 이름 `EMAIL_FROM`, 환경 **Production**, 값 `K-Coupon Japan <noreply@(B에서 Verified된 도메인)>` → Save
- **순서**: Save → Deployments → 최신 배포 `⋯` → **Redeploy** → 완료(Ready) 후 본인 주소 2개(Resend 계정 주소 + 다른 주소)로 가입 → 인증 메일 수신 → 링크 클릭
- **성공 확인**: 두 주소 모두 수신, 마이페이지의 "メールアドレスがまだ確認されていません"가 사라짐, Sentry에 `email:` 오류 없음
- **중단 조건**: 메일이 안 오거나 Sentry에 `email: Resend rejected the send (403 …)` → Resend → Logs에서 사유 확인(403 = 도메인 미인증/발신 주소 불일치, 422 = 주소 형식). 이때 사이트는 "メールを送信できません"을 정직하게 보여주고 있으므로 이용자에게 잘못된 안내는 나가지 않습니다.
- (같은 화면에서) **Settings → Cron Jobs**에서 `/api/cron/notify`가 등록돼 있고 마지막 실행 기록이 있는지만 확인 (2-8번)

### D. Sentry — 오류가 실제로 오는지 (코드는 보내고 있지만 도착은 화면에서만 확인됨)

## 1. 쿠폰 사용 처리 — 출시 시점 운영 방식

**결정: 출시 초기에는 A안(관리자 대리 처리)을 사용하고, 매장 직원 계정은 만들지 않는다.**

| | A. 관리자 대리 처리 (권장 · 구현 불필요) | B. 매장별 직원 계정 |
|---|---|---|
| 방식 | 매장에서 이용자의 쿠폰 코드(또는 QR)를 확인 → 운영자가 `/admin/redeem`에서 코드 입력/QR 스캔 후 "使用処理する" | 매장 직원이 본인 계정으로 로그인해 자기 매장 쿠폰만 처리 |
| 필요한 개발 | 없음 (이미 동작) | 직원 계정 테이블, 매장 연결, 매장별 권한(서버+DB), 계정 생성/비활성 화면, 처리자 기록 — 중간 규모 |
| 장점 | 즉시 가능, 권한 사고 위험 낮음 | 운영자 병목 없음 |
| 단점 | 운영자가 실시간 대기해야 함 → 제휴 매장이 늘면 한계 | 보안 설계·테스트 부담 |
| 적합 시점 | 제휴 매장 ~5곳, 사용량이 적을 때 | 매장 5곳 이상 또는 사용 요청이 하루 수십 건을 넘을 때 |

### A안 운영 절차
1. 이용자가 매장에서 마이페이지의 QR(또는 코드)을 제시한다.
2. 매장이 운영자에게 코드를 전달한다 (LINE/카카오톡 등). **QR 이미지 스캔 또는 코드 문자열.**
3. 운영자가 `/admin/redeem` → 코드 입력(또는 "QR" 버튼) → 매장명·쿠폰명·회원 닉네임 확인 → "使用処理する".
4. 결과가 "使用処理が完了しました"인지 확인하고 매장에 회신한다. 이미 사용/만료/중지 쿠폰은 화면에 이유가 표시된다.
5. 사용 처리는 1회만 가능하다 (DB 유니크 인덱스로 동시 중복 처리도 차단).
6. **약속 시간**: 매장에 "코드 확인 회신은 영업시간 중 N분 이내"처럼 기대치를 사전에 안내한다 (사업 결정).

> B안은 제휴 매장 수·처리량이 위 기준을 넘을 때 별도 작업으로 설계한다 (전체 관리자 권한을 주지 않고, 본인 매장 쿠폰만 서버+DB에서 검증).

### 현재 코드 기준의 사실 (2026-10-21 코드 조사)
| 질문 | 답 |
|---|---|
| 직원은 어떤 화면에서 확인하는가 | 직원 전용 화면은 **없음**. `/admin/redeem`(관리자 전용)만 있음 → A안은 운영자가 대신 처리 |
| 누가 사용 처리할 수 있는가 | 서버 액션 `processRedeem`이 `requireAdmin()`으로 막음 (관리자 이메일 목록 + DB 조회). 일반 이용자·비로그인은 불가 |
| QR에는 무엇이 들어 있는가 | 발급 이벤트 UUID 하나뿐. 이름·이메일 등 개인정보 없음. 사용 처리되면 무효 |
| 중복 사용은 어떻게 막는가 | 처리 직전 재확인 + DB 부분 유니크 인덱스(회원·쿠폰·사이클). 동시 처리돼도 한쪽 insert가 실패(23505)하며 그때는 포인트도 안 줌 |
| 만료·중지 쿠폰은 | 처리 직전에 유효기간(KST)·쿠폰/매장 활성 여부를 다시 확인해 거부 |
| 사용 이력을 추적할 수 있는가 | `coupon_events`의 `use` 행(쿠폰·회원·시각)은 남음. **"누가 처리했는지"는 남지 않음** (B안에서 `redeemed_by` 추가 필요) |
| QR 스크린샷이 공유되면 | 사용 처리는 1회만 되지만, 스크린샷을 가진 다른 사람이 먼저 처리를 요청할 수는 있음. 매장은 마이페이지 화면의 닉네임·쿠폰명과 대조하도록 안내 |

### B안 최소 설계안 (구현 전에 승인 필요 — 현재 코드에는 없음)
기존 권한 구조(관리자 = `ADMIN_EMAILS` + DB 조회, `users`에 role 컬럼 없음)를 바꾸지 않고 **매장별 직원 연결만 추가**합니다.
1. 테이블 `store_staff(user_id → users, store_id → stores, created_at, primary key(user_id, store_id))` — RLS 켜고 정책 없음(서버만 접근)
2. `coupon_events.redeemed_by uuid null` 컬럼 추가 (처리한 직원/관리자 기록)
3. 서버 검사 `requireStaffForStore(storeId)`: 세션 사용자가 그 매장의 직원이거나 관리자일 때만 통과
4. 직원 화면 `/staff/redeem`: 코드의 쿠폰이 **본인 소속 매장**의 것일 때만 조회·처리, 아니면 "この店舗のクーポンではありません" (기존 `processRedeem` 로직 재사용)
5. 직원 계정은 관리자 화면에서만 연결·해제 (직원 자가 가입 없음). 퇴사·계약 종료 시 즉시 해제
6. 필수 테스트: 다른 매장 코드 거부 / 직원 아닌 계정 거부 / 해제된 직원 거부 / 동시 2회 처리 시 1회만 성공 / `redeemed_by` 기록

### 2-7. Sentry 오류 수신 확인 (운영자가 직접)
코드는 서버·브라우저 모두 `SENTRY_DSN`/`NEXT_PUBLIC_SENTRY_DSN`이 있으면 자동으로 오류를 보냅니다. (Sentry SDK 11.1.0에는 개인정보 전송을 끄는 별도 옵션이 없어 기본 설정을 그대로 씁니다. 이 앱이 직접 만드는 오류 메시지에는 이메일·토큰이 들어가지 않지만, SDK가 자동으로 붙이는 요청 정보까지 확인한 것은 아니므로 **이벤트를 처음 받으면 상세 화면에서 IP·쿠키·이메일이 없는지 직접 확인**하세요.) 하지만 **이벤트가 실제로 도착하는지는 Sentry 화면에서만 확인할 수 있어서** 아직 검증되지 않았습니다.
- [ ] Sentry → Projects → 이 프로젝트 → Settings → Client Keys의 DSN이 Vercel의 `SENTRY_DSN`·`NEXT_PUBLIC_SENTRY_DSN`과 같은 프로젝트인가
- [ ] 안전하게 이벤트를 만드는 방법: 로그인하지 않은 상태에서 가입 화면의 메일 발송이 실패하는 상황이 가장 자연스럽습니다 (6번 도메인 설정 전에는 본인 외 주소로 가입/재설정 시 `email: Resend rejected the send (403 …)`이 Sentry에 올라와야 정상). 이 이벤트가 보이면 서버 → Sentry 경로는 검증된 것입니다
- [ ] 이벤트 상세에 이메일 주소·토큰이 없는지 확인 (코드는 `t***@도메인` 형태로 마스킹하고 응답 본문은 기록하지 않음)
- [ ] 알림 규칙: Alerts에서 "새 이슈 발생 시 이메일"을 켜 두기 (켜지 않으면 이벤트가 쌓여도 아무도 모릅니다)

### 2-8. 크론 확인 (LINE 알림을 실제로 보내지 않고)
`vercel.json`: `0 0 * * *` (UTC 00:00 = 한국 09:00). Vercel 크론은 `CRON_SECRET`이 설정돼 있으면 `Authorization: Bearer …`를 자동으로 붙여 호출하고, 코드는 그 값이 맞지 않으면 401을 돌려줍니다.
- 401 응답만으로는 "크론이 돌고 있다"를 증명할 수 없습니다. 아래 둘을 확인하세요.
- [ ] Vercel → Project → Settings → **Cron Jobs**에서 `/api/cron/notify`가 등록돼 있고 마지막 실행 시각·결과가 있는가 (Hobby 플랜은 지정한 시각이 아니라 그 시(時) 안의 임의 시각에 실행될 수 있음)
- [ ] **dryRun 호출 (메시지를 보내지 않고 대상 건수만 반환)**: PowerShell에서
  ```powershell
  $s = Read-Host "CRON_SECRET" -AsSecureString   # 화면에 보이지 않게 입력
  $t = [Runtime.InteropServices.Marshal]::PtrToStringAuto([Runtime.InteropServices.Marshal]::SecureStringToBSTR($s))
  Invoke-RestMethod -Uri "https://japan-coupon-five.vercel.app/api/cron/notify?dryRun=1" -Headers @{ Authorization = "Bearer $t" }
  ```
  기대 결과: `ok: true, dryRun: true, targetDate: …, couponsSent: N, travelSent: M, failed: 0` (N/M은 "보냈다면 몇 건"). `dryRun=1` 없이 호출하면 **실제로 LINE이 발송**되니 주의
- [ ] 중복 실행: 같은 날 두 번 호출되면 같은 안내가 두 번 갈 수 있습니다 (발송 기록 테이블이 없음 — 출시 후 개선 후보, 현재 대상 규모에서는 영향이 작음)

### 2-9. 메일 실발송 확인 (본인 주소로만)

## 4-2. DB 마이그레이션 (직접 실행 — Supabase SQL Editor의 **새 쿼리 탭**에 파일 내용만 붙여넣기)

두 파일 모두 **추가형(additive)** 이라 기존 데이터를 바꾸거나 지우지 않고, 여러 번 실행해도 안전합니다 (로컬 PostgreSQL에서 두 번 연속 실행 + 적용 전/후 검증 쿼리까지 테스트함).
**2026-10-21에 두 파일이 보강되었습니다** (`search_path`에 `pg_temp` 명시, 사용자 존재·쿠폰 활성·만료 검사 추가). 아직 운영에 적용 전이므로 이전 버전을 따로 실행하셨다면 다시 실행해도 안전하게 덮어씁니다.

**현재 운영 DB 상태 (2026-10-21 읽기 전용 조회)**: `issue_coupon`·`use_points` 함수 없음, `point_events.request_id`·`purpose` 컬럼 없음 → **두 마이그레이션 모두 미적용**. `coupon_events.reissue_key` 컬럼은 있음.
**미적용 상태에서 앱이 하는 일**: 수량 제한이 **없는** 쿠폰은 이전 방식으로 정상 발급. 수량 제한이 **있는** 쿠폰은 발급하지 않고 "ただいまこのクーポンを発行できません"을 보여주며 Sentry에 `issue_coupon() is missing…` 오류를 올림 (한도를 조용히 넘겨 발급하는 것보다 안전). 지금은 공개 쿠폰이 0개라 영향 없음.

- Vercel Production에 `EMAIL_FROM`이 **없습니다**. 로컬 `.env.local`의 `EMAIL_FROM`도 Resend 공용 주소(`resend.dev`)라서, **어디에도 자체 도메인 발신 설정이 없습니다.**
- 이 경우 코드는 `onboarding@resend.dev`로 발송을 시도하고, Resend는 이 주소에서 **계정 소유자 본인 주소로만** 발송을 허용합니다 → 일반 이용자에게는 인증·재설정 메일이 도착하지 않을 가능성이 높습니다.
- Resend API 키는 "발송 전용"으로 제한돼 있어 코드로는 도메인 인증 상태를 **조회할 수 없습니다** (최소 권한이라 정상). 인증 상태는 Resend 대시보드에서만 확인됩니다 → 검증 불가 항목.

### 2026-10-21 코드 변경 (메일이 실패할 때 조용히 지나가지 않도록)
- `sendEmail()`은 예외를 던지지 않고 성공/실패 결과를 돌려줍니다. 실패하면 **Sentry에 오류가 올라갑니다** (상태 코드와 오류 종류만, 수신자 주소는 `t***@도메인` 형태로 마스킹, Resend 응답 본문은 기록하지 않음).
- **운영에서 `EMAIL_FROM`이 비어 있으면 메일을 보내지 않습니다.** (이전에는 Resend 공용 주소로 대체했는데, 그 주소는 일반 이용자에게 도착하지 않아 "보냈다"는 착각만 만들었습니다.) 형식이 잘못된 값(꺾쇠·개행 등 헤더 주입 포함)도 보내지 않으며, 두 경우 모두 Sentry에 오류가 올라갑니다 (같은 오류는 서버 인스턴스당 한 번). 개발·테스트 환경(production이 아닐 때)에서만 빈 값이 공용 주소로 대체됩니다.
- 운영자가 **본인 주소로만** 먼저 시험하고 싶다면 Vercel의 `EMAIL_FROM`에 `onboarding@resend.dev`를 **명시적으로** 넣으면 됩니다 (이때도 Sentry에 "sandbox" 경고가 한 번 올라옵니다). 일반 이용자용 설정은 아래 1~9단계로 끝냅니다.
- 마이페이지 "確認メールを再送する"는 **실제로 보냈을 때만** "再送しました"를 보여주고, 실패하면 오류 문구를 보여줍니다. 회원당 1시간 5회 제한.
- **비밀번호 재설정**: 메일 설정이 갖춰지지 않았으면 "現在、メールを送信できません"을 보여줍니다 (입력한 주소와 무관하게 모든 요청에 똑같이 적용되므로 계정 존재 여부를 알려주지 않음). 설정이 갖춰져 있으면 "ご入力のメールアドレスが登録されている場合、再設定用のメールを送信しました"를 보여줍니다 — 가입되지 않은 주소에는 실제로 아무것도 보내지 않으므로 "送信しました"라고 단정하지 않습니다. 설정은 되어 있는데 Resend가 거절하는 경우(예: 도메인 미인증)는 응답 뒤에 처리되어 화면에는 드러나지 않고 Sentry로만 확인됩니다.
- **가입**: 인증 메일 발송이 실패해도 가입은 진행되지만, 온보딩 첫 화면에 "確認メールを送信できませんでした…あとでマイページから再送できます"가 표시됩니다 (인증이 끝난 것처럼 보이지 않음).
- 자동 재시도는 넣지 않았습니다 (재시도하면 같은 메일이 두 번 갈 수 있음). 가입은 메일 발송 성공과 무관하게 진행되고, 인증은 나중에 마이페이지에서 다시 요청할 수 있습니다.
- 링크는 `NEXT_PUBLIC_SITE_URL`로 만들어집니다 → 도메인을 바꾸면 이 값을 함께 바꾸세요 (3번).

### 운영자가 할 일 (순서대로)
1. [ ] **발신 도메인 결정**: 예) `mail.<서비스 도메인>` 같은 서브도메인을 쓰면 본 도메인의 기존 메일 설정과 섞이지 않습니다. (도메인이 없으면 먼저 3번)
2. [ ] **Resend 대시보드 → Domains → Add Domain**: 위 도메인과 리전(일본 이용자라면 가까운 리전)을 입력
3. [ ] **DNS 레코드 등록**: Resend가 화면에 보여주는 SPF·DKIM(+ 필요 시 DMARC) 레코드를 **그 값 그대로** 도메인 DNS(가비아/Cloudflare 등)에 추가. 값을 임의로 만들거나 줄이지 마세요
4. [ ] **Verify** 버튼 → 상태가 **Verified**가 될 때까지 대기 (몇 분~수 시간). Failed/Pending이면 레코드 오타·중복 레코드를 확인
5. [ ] **발신 주소 결정**: 예) `K-Coupon Japan <noreply@mail.도메인>` (표시 이름에 따옴표·꺾쇠는 쓰지 않음)
6. [ ] **Vercel → Project → Settings → Environment Variables**: `EMAIL_FROM`을 Production에 추가 (값은 5번)
7. [ ] **재배포**: 환경변수는 새 배포부터 적용됩니다 (Deployments → 최신 배포 → Redeploy, 또는 빈 커밋 푸시)
8. [ ] **테스트 발송**: 2-9번대로 **운영자 본인 주소 2개**(Resend 계정 주소, 다른 도메인 주소)로 가입 → 수신
9. [ ] **수신·링크 확인**: 메일이 스팸함이 아닌 받은편지함에 도착하는가, 링크가 새 도메인으로 열리는가, 인증 후 마이페이지의 경고가 사라지는가. Sentry에 `email:` 오류가 없는가

- 성공 확인: 본인 외 주소로도 메일이 도착하고 Sentry에 `email: Resend rejected…`가 더 이상 올라오지 않는다.
- 실패 시: Resend → Logs에서 해당 발송의 상태와 사유를 확인 (403 `validation_error` = 도메인 미인증/주소 불일치, 422 = 주소 형식, 401 = API 키). Sentry 이벤트의 `status` 태그와 대조.
- 그 전까지 임시 안내: 이메일 가입자가 비밀번호를 잊으면 Google/LINE 로그인을 안내하거나 운영자가 대응한다. 제한적 베타 이전에는 반드시 완료.

## 10. 실제 운영 기능 검증 계획 — 현재 상태

격리된 테스트 환경이 아직 없습니다: 로컬 서버와 배포 모두 **운영 Supabase 하나**를 가리키므로, 가입·발급·사용·메일 같은 쓰기 동작을 운영 데이터와 분리해 시험할 수 없습니다. 아래 상태는 이 제약 때문에 `BLOCKED`로 둔 항목입니다.

| 영역 | 자동 검증(코드·DB) | 운영 실행 검증 |
|---|---|---|
| 회원가입·로그인·로그아웃·세션 | 코드 리뷰, 비로그인 차단 확인 | **BLOCKED** (테스트 계정·격리 환경 필요) |
| 이메일 인증·비밀번호 재설정 | 단위 테스트(발신 주소 검증), 코드 리뷰 | **BLOCKED** (도메인 인증 + 본인 주소, 2-9) |
| OAuth(Google·LINE) | 코드 리뷰 | **BLOCKED** (실제 공급자 계정, 2-1·2-2) |
| 쿠폰 발급·중복·수량 | DB 테스트 32건(동시성 포함) | **BLOCKED** (운영 DB에 함수 미적용) |
| 쿠폰 사용·중복 사용 | DB 유니크 인덱스, 코드 리뷰 | **BLOCKED** (테스트 쿠폰 필요, 9-3) |
| 포인트 | DB 테스트 27건 | NOT APPLICABLE (사용 기능은 꺼져 있음) |
| 크론 | dryRun 모드 로컬 검증 | **BLOCKED** (실행 로그·dryRun 운영 호출, 2-8) |
| Sentry 수신 | 코드 리뷰 | **BLOCKED** (Sentry 화면 확인, 2-7) |
| 실기기·카메라 | 320/375px 에뮬레이션 | **BLOCKED** (실기기, 2-3·2-10) |

### 격리 테스트 환경을 만드는 방법 (운영자 작업이 필요)
1. Supabase에서 **새 프로젝트**(예: `k-coupon-staging`)를 만든다 — 운영 프로젝트와 완전히 분리
2. 운영 스키마를 그 프로젝트에 복제한다 (기본 스키마 SQL은 저장소에 없으므로 운영 프로젝트에서 스키마만 내보내기 → 새 프로젝트에 실행. **운영 데이터는 가져오지 않는다**) 후 `db/migrations/*.sql`과 `db/verify/post-apply-check.sql` 실행
3. Vercel **Preview** 환경변수에 테스트용 값을 넣는다: 새 Supabase URL/키, 별도 `AUTH_SECRET`, 테스트용 `EMAIL_FROM`/Resend 키(본인 주소만 수신), LINE·Google은 개발용 채널
4. 테스트 계정·테스트 쿠폰·테스트 매장을 만들고, 끝나면 **프로젝트째 비운다** (운영과 분리돼 있어 삭제 위험이 없음)
5. 이 환경에서 위 표의 BLOCKED 항목을 순서대로 실행 → 결과를 이 표에 기록

> 기본 스키마가 저장소에 없다는 점은 그 자체로 위험 요소입니다 (운영 DB가 손상되면 코드만으로 복원할 수 없음). Supabase의 백업(Dashboard → Database → Backups) 사용 가능 여부를 확인하고, 스키마 SQL을 `db/schema/`에 보관하는 것을 권장합니다.

## 12. 장애 대응과 모니터링

### 12-1. 쿠폰 발급을 멈추는 방법 (빠른 순서)
1. **특정 쿠폰만** — 관리자 `/admin/coupons` → 해당 쿠폰 편집 → `掲載を有効にする` OFF. 공개 목록에서 즉시 사라지고 발급이 막힙니다 (서버가 `is_active`를 확인).
2. **모든 쿠폰의 발급을 DB에서 즉시 차단** (함수를 설치한 뒤에만 해당) — Supabase SQL Editor 새 탭에서:
   ```sql
   revoke execute on function public.issue_coupon(uuid, uuid, text) from service_role;
   ```
   앱이 권한 오류(42501)를 받으면 **어떤 쿠폰도 발급하지 않고** 상세 화면으로 돌려보내며 Sentry에 `issue_coupon failed (42501)`를 올립니다 (코드가 "함수 없음(PGRST202)"이 아닌 오류에서는 절대 예비 경로로 넘어가지 않음 — 단위 테스트됨). 재개: 같은 탭에서
   ```sql
   grant execute on function public.issue_coupon(uuid, uuid, text) to service_role;
   ```
   (함수가 아직 설치되지 않았다면 이 방법은 필요 없습니다 — 그 상태에서는 수량 제한 쿠폰이 이미 막혀 있고, 수량 제한이 없는 쿠폰은 1번으로 내리세요.)
3. **코드 되돌리기** — 12-2번.
4. 신규 가입만 멈추려면 `src/lib/feature-flags.ts`의 `SIGNUPS_ENABLED`(이미 있는 스위치)를 `false`로 바꾸고 배포합니다.

### 12-2. 이전 배포로 롤백
```bash
vercel ls                          # 가장 최근의 이전 Ready 배포를 찾는다
vercel rollback <그 배포의 URL>      # 운영 도메인이 그 배포를 가리키게 됨
npm run smoke -- https://japan-coupon-five.vercel.app   # 홈·접근 제어·헤더 확인
```
대시보드로 하려면 Vercel → Deployments → 이전 배포 `⋯` → **Promote to Production**. 코드 롤백은 DB를 건드리지 않습니다. SQL 함수는 추가형이라 어떤 버전의 코드로 돌아가도 호환됩니다 (옛 코드는 함수를 호출하지 않거나, 있으면 같은 방식으로 호출).

### 12-3. 모니터링 — 코드가 하는 일과, 실제로 확인된 것
코드에 알림 장치가 있다는 사실과 **실제로 알림이 도착한다**는 사실은 다릅니다. 아래 "확인" 열이 `BLOCKED`인 것은 운영 대시보드에서만 확인할 수 있는 항목입니다.

| 신호 | 코드가 하는 일 | 보는 곳 | 확인 |
|---|---|---|---|
| 서버·브라우저 예외 | Sentry가 자동 수집 (SDK 기본 설정. 이벤트 상세에 IP·쿠키·이메일이 없는지 처음 받을 때 직접 확인) | Sentry → Issues | BLOCKED (도착 미확인, D 참고) |
| 메일 설정 누락/잘못됨/거절/네트워크 오류 | Sentry 메시지 `email: …` (수신자 마스킹, 응답 본문 미기록) | Sentry → Issues, Resend → Logs | BLOCKED |
| 쿠폰 발급 오류 | `issue_coupon failed (코드)` · `issue_coupon() is missing…`(수량 제한 쿠폰 차단) · `issue (legacy path) failed` | Sentry | BLOCKED |
| 사용 처리 오류 | `redeem: …` (이벤트 ID만 포함, 개인정보 없음) | Sentry | BLOCKED |
| 크론 | 실패하면 Sentry `cron/notify`; LINE 발송 실패 건수가 있으면 경고 | Vercel → Cron Jobs / Logs, Sentry | 정기 실행은 로그 1건으로 추정, 대시보드 확인 필요 |
| 크론 중복 실행 | 같은 날 두 번 호출되면 같은 안내가 두 번 갈 수 있음 (발송 기록 테이블 없음) | — | 알려진 한계 (대상 규모가 작아 영향 작음; 발송 기록 테이블은 출시 후 개선) |
| LINE 웹훅 인증 실패 | 401만 반환 (외부 스캐너로 Sentry가 가득 차지 않게 알림은 보내지 않음) | Vercel Logs에서 `POST /api/line/webhook 401` | 정상 LINE 트래픽에서 401이 갑자기 늘면 secret 불일치(4-1-b) |
| 로그의 개인정보 | 이메일은 `t***@도메인`, 토큰·API 키·Resend 응답 본문은 기록하지 않음, 위치 좌표는 기록하지 않음 | Vercel Logs | 코드 리뷰로 확인 (운영 로그 전수 확인은 아님) |

운영자가 Sentry에서 켜야 하는 것: Alerts → **새 이슈가 생기면 이메일**. 켜지 않으면 이벤트가 쌓여도 아무도 모릅니다.
