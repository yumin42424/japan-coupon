## 1. 쿠폰 사용 처리 — 출시 시점 운영 방식

**결정: 출시 초기에는 A안(관리자 대리 처리)을 사용하고, 매장 직원 계정은 만들지 않는다.**

| | A. 관리자 대리 처리 (권장 · 구현 불필요) | B. 매장별 직원 계정 |
|---|---|---|
| 방식 | 매장에서 이용자의 쿠폰 코드(또는 QR)를 확인 → 운영자가 `/admin/redeem`에서 코드 입력/QR 스캔 후 "使用処理する" | 매장 직원이 본인 계정으로 로그인해 자기 매장 쿠폰만 처리 |
| 필요한 개발 | 없음 (이미 동작) | 직원 계정 테이블, 매장 연결, 매장별 권한(서버+DB), 계정 생성/비활성 화면, 처리자 기록 — 중간 규모 |
| 장점 | 즉시 가능, 권한 사고 위험 낮음 | 운영자 병목 없음 |
| 단점 | 운영자가 실시간 대기해야 함 → 제휴 매장이 늘면 한계 | 보안 설계·테스트 부담 |
| 적합 시점 | 제휴 매장 ~5곳, 사용량이 적을 때 | 매장 5곳 이상 또는 사용 요청이 하루 수십 건을 넘을 때 |

### A안 운영 절차
1. 이용자가 매장에서 마이페이지의 QR(또는 코드)을 제시한다.
2. 매장이 운영자에게 코드를 전달한다 (LINE/카카오톡 등). **QR 이미지 스캔 또는 코드 문자열.**
3. 운영자가 `/admin/redeem` → 코드 입력(또는 "QR" 버튼) → 매장명·쿠폰명·회원 닉네임 확인 → "使用処理する".
4. 결과가 "使用処理が完了しました"인지 확인하고 매장에 회신한다. 이미 사용/만료/중지 쿠폰은 화면에 이유가 표시된다.
5. 사용 처리는 1회만 가능하다 (DB 유니크 인덱스로 동시 중복 처리도 차단).
6. **약속 시간**: 매장에 "코드 확인 회신은 영업시간 중 N분 이내"처럼 기대치를 사전에 안내한다 (사업 결정).

> B안은 제휴 매장 수·처리량이 위 기준을 넘을 때 별도 작업으로 설계한다 (전체 관리자 권한을 주지 않고, 본인 매장 쿠폰만 서버+DB에서 검증).

## 2. 실기기 테스트 절차 (코드 검증으로는 대신할 수 없는 항목)

> 아래는 모두 **운영 사이트**에서 **본인 계정**으로 수행합니다. 테스트용 쿠폰은 관리자 화면에서 만든 뒤, 끝나면 `掲載を有効にする`를 꺼 두거나 삭제하세요.

### 2-1. Google 로그인
- [ ] 시크릿 창 → `/signup` → "Googleで登録" → 동의 체크 후 진행 → 로그인 완료 → `/onboarding`으로 이동하는가
- [ ] 로그아웃 후 `/login` → "Googleでログイン" → 마이페이지 도달
- [ ] 동의 체크 없이 "Google"을 눌렀을 때 가입이 거부되는가
- [ ] **Google Cloud Console → OAuth 클라이언트 → 승인된 리디렉션 URI**에 현재 주소의 `/api/auth/callback/google`이 있고, `localhost`·옛 임시 주소가 남아 있지 않은가
- [ ] OAuth 동의 화면의 앱 상태(테스트/프로덕션), 앱 이름·지원 이메일·개인정보 URL

### 2-2. LINE 로그인 / LINE Messaging
- [ ] **LINE Developers → LINE Login 채널 → Callback URL**에 `…/api/auth/callback/line`이 등록돼 있고 채널이 "公開済み"인가
- [ ] 일본 앱스토어 LINE 또는 일본 계정으로 `/signup` → "LINEで登録" → 완료
- [ ] 같은 LINE 계정으로 재로그인 시 새 계정이 만들어지지 않고 기존 계정으로 들어오는가
- [ ] **Messaging API 채널 → Webhook URL** = `…/api/line/webhook`, "Webhookの利用"이 ON, "検証" 버튼이 성공하는가
- [ ] 공식계정을 친구 추가 → 텍스트 전송 → 안내 문구 응답
- [ ] **위치 전송**(일본 앱스토어 LINE에서만 메뉴 존재) → 5km 내 공개 쿠폰이 있을 때 카드 응답 / 없을 때 "この辺りにはまだクーポンがありません"
- [ ] LINE Login 채널과 Messaging 채널이 **같은 Provider**에 있는가 (아니면 `line_user_id`가 달라 push가 실패함)

### 2-3. QR 카메라 스캔 (관리자 → 사용 처리)
- [ ] iPhone Safari / Android Chrome에서 `/admin/redeem` → QR 버튼 → 카메라 권한 허용 → 마이페이지 QR을 스캔 → 코드 자동 입력 후 조회
- [ ] 권한 **거부** 시 오류 안내가 보이고 코드 직접 입력이 가능한가
- [ ] `BarcodeDetector` 미지원 브라우저(구형 Safari 등)에서는 QR 버튼이 숨겨지고 직접 입력이 가능한가
- [ ] 잘못된 QR(다른 문자열) → "コードが見つかりません"
- [ ] 만료된 쿠폰 / 이미 사용한 쿠폰 / 중지된 쿠폰 → 각각 해당 안내
- [ ] 같은 QR을 연속으로 두 번 처리 → 두 번째는 "既に使用済み"
- [ ] 비행기 모드(네트워크 오류)에서 처리 시도 → 오류 후 재시도 가능한가

### 2-4. LINE 알림 실발송
- [ ] 본인 LINE 계정으로 가입 + 마케팅 수신 동의 + 관심지역 설정
- [ ] 관리자에서 해당 지역에 **새 매장 등록** → LINE push 도착 (판촉이므로 동의한 회원에게만 간다)
- [ ] 만료 3일 전 알림: 테스트 쿠폰의 `終了日`을 오늘+3일로 하고 GET → 다음 날 아침 9시(KST) cron 실행 후 도착 확인
  (cron 확인: Vercel → Project → Cron Jobs → 실행 로그 / 즉시 확인은 `curl -H "Authorization: Bearer $CRON_SECRET" https://<주소>/api/cron/notify`)
- [ ] 여행일 임박 알림: 마이페이지에서 여행일을 오늘+3일로 설정(마케팅 동의 회원만 대상)
- [ ] push 실패 시 로그에 토큰/개인정보가 남지 않는가 (Vercel Logs 확인)

### 2-5. 관리자 화면 (로그인 후)
- [ ] 비밀번호로 로그인 → `/admin` 지표 표시
- [ ] 매장 등록 (좌표는 한국 범위 33~39 / 124~132만 허용) → 쿠폰 등록(가격은 **원화(₩) 정수**) → 공개 화면 확인
- [ ] 쿠폰 수정에서 `再利用間隔`, `数量制限` 입력/저장
- [ ] 비관리자 계정으로 `/admin`·`/admin/coupons` 직접 접근 → 홈으로 이동

### 2-6. 회원 흐름
- [ ] 이메일 가입 → 온보딩 → 쿠폰 GET → 마이페이지에 QR 표시
- [ ] 비밀번호 재설정 메일이 **본인 외 다른 주소**로도 도착하는가 (→ 6번 "메일 발신 도메인" 완료 전에는 실패하는 것이 정상)
- [ ] 회원 탈퇴 → 다시 같은 이메일로 가입 가능 + 리뷰 사진이 스토리지에서 삭제됨

## 3. 정식 도메인 전환 체크리스트

도메인 구입·DNS 설정은 직접 해야 합니다 (코드에서 대신하지 않음).

1. [ ] 도메인 구입 → Vercel → Project → Settings → Domains에 추가 → DNS 레코드 설정 → HTTPS 발급 확인
2. [ ] Vercel 환경변수 `NEXT_PUBLIC_SITE_URL`을 새 주소로 변경 (Production) → **재배포**
   (canonical/OpenGraph/sitemap/robots/이메일 링크/LINE 공유 링크/관리 알림 링크가 모두 이 값을 따른다)
3. [ ] Google Cloud Console: 승인된 JavaScript 원본 + 리디렉션 URI(`/api/auth/callback/google`)에 새 주소 추가, 옛 주소 제거
4. [ ] LINE Login 채널: Callback URL에 `/api/auth/callback/line` 새 주소 추가, 옛 주소 제거
5. [ ] LINE Messaging 채널: Webhook URL을 새 주소로 변경 후 "検証"
6. [ ] Kakao Developers(지도): 플랫폼 > Web 도메인에 새 주소 추가
7. [ ] Resend: 발신 도메인 인증 (6번)
8. [ ] Supabase: Authentication 설정은 사용하지 않지만 Storage CORS/URL 설정이 있다면 확인 (이 앱은 Supabase Auth 미사용)
9. [ ] 전환 후 재검증: 로그인(이메일/Google/LINE) → 쿠폰 GET → 마이페이지 → 비밀번호 재설정 메일 링크 → LINE 공유 링크 → `view-source`에서 canonical이 새 주소인지
10. [ ] 옛 `*.vercel.app` 주소는 새 도메인으로 301 리다이렉트하거나 그대로 두되 canonical은 새 도메인을 가리키는지 확인

## 4. 비밀키 교체 (Rotation)

원칙: **외부 서비스에서 폐기·재발급 → Vercel 환경변수 교체 → 재배포 → 옛 키 무효화 확인** 순서. 키를 채팅/메신저로 공유하지 않는다.

| 항목 | 현재 상태(증거) | 해야 할 일 |
|---|---|---|
| Supabase service role / publishable key | Vercel 값 생성일 9/14, 옛 JWT 키 비활성화 보고됨 | 완료로 보이나 Supabase 대시보드에서 "Disable JWT-based API keys" 상태 재확인 |
| `AUTH_SECRET` | Vercel 값 9/11 | 완료로 보임. 교체 시 모든 로그인 세션이 풀리므로 영향 인지 |
| LINE Login Channel Secret (`AUTH_LINE_SECRET`) | Vercel 값 9/14 (교체 여부 **미확인**) | LINE Developers → 채널 → "Channel secret" 재발급 가능 여부 확인 후 교체 |
| LINE Messaging Channel Secret / Access Token | Vercel 값 9/11 — **미교체** | Messaging API 채널에서 Channel secret 재발급, Channel access token 재발급 → Vercel 교체 |
| Google OAuth Client Secret | Vercel 값 8/22 — **미교체** | Google Cloud Console → 사용자 인증 정보 → 클라이언트 보안 비밀번호 새로 추가 → Vercel 교체 → 옛 비밀 삭제 |
| Kakao 지도 JavaScript 키 | 공개 키(`NEXT_PUBLIC_`)이므로 비밀이 아님 | 도메인 제한이 새 주소로 설정돼 있는지만 확인 |
| 관리자 비밀번호 | **미교체(보류 상태)** | `/mypage/settings`에서 변경 (현재 비밀번호 필요). 길고 고유한 비밀번호 권장 |
| `CRON_SECRET` | 10/2 신규 생성 | 이상 없음 |
| Resend API 키 | "발송 전용" 제한 키 | 이상 없음 (도메인 조회 불가 = 최소 권한 정상) |

Git 이력 점검 결과: `.env*` 파일이 커밋된 적 없음, 현재/과거 비밀값 패턴 0건 → **코드 저장소에서 새어 나간 비밀은 없음**. 교체 필요 사유는 채팅 등 코드 밖 노출 이력뿐이다.

## 4-2. DB 마이그레이션 (직접 실행 — Supabase SQL Editor의 **새 쿼리 탭**에 파일 내용만 붙여넣기)

두 파일 모두 **추가형(additive)** 이라 기존 데이터를 바꾸거나 지우지 않고, 여러 번 실행해도 안전합니다. 적용하지 않아도 앱은 지금 동작 그대로 작동합니다.

| 파일 | 하는 일 | 권장 시점 |
|---|---|---|
| `db/migrations/20261012_issue_coupon_atomic.sql` | 선착순(수량 제한) 쿠폰 발급을 DB에서 원자적으로 처리 → 동시에 몰려도 정확히 N명만 발급 (실제 PostgreSQL에서 동시 20건 → 정확히 3건 발급 검증) | **수량 제한이 있는 쿠폰을 처음 만들기 전** (한도 없는 쿠폰만 쓴다면 급하지 않음) |
| `db/migrations/20261012_point_use.sql` | 포인트 사용(차감) 함수 + 내역 컬럼. 사용처가 정해질 때까지 앱은 사용을 서버에서 거부함 | 포인트 사용처가 확정되어 기능을 켤 때 |

적용 확인: SQL Editor에서 `select proname from pg_proc where proname in ('issue_coupon','use_points');`

## 5. 포인트 사용 기능 활성화 절차 (사업 정책 확정 후)

현재 `src/lib/point-policy.ts`의 `POINT_USE_ENABLED = false`, `POINT_USE_OPTIONS = []` → 서버가 모든 사용 요청을 `disabled`로 거부하고 UI는 "ポイントの利用機能は準備中です"를 표시한다.

활성화 순서:
1. [ ] 사용처·차감 포인트·사용 조건을 사업적으로 결정한다 (예: 무엇과 교환되는가, 유효기간이 있는가, 환불은 어떻게 하는가 — 이용약관에 반영 필요)
2. [ ] Supabase SQL Editor → **새 쿼리 탭**에 `db/migrations/20261012_point_use.sql` 내용만 붙여넣고 실행 (기존 데이터는 변경되지 않음)
3. [ ] `POINT_USE_OPTIONS`에 사용처를 추가하고 `POINT_USE_ENABLED = true`
4. [ ] 스테이징(또는 테스트 계정)에서 12개 시나리오 재검증 후 배포
   (자동 테스트: `npm test` + `db/tests/point-use.sql-test.mjs`)
5. [ ] 이미 적립된 포인트의 법적 지위(이용자에게 약속된 보상인지)를 정리한다 — 임의로 소멸시키지 않는다

포인트 화면 전체를 숨기려면 `POINT_UI_VISIBLE = false` 한 줄(데이터는 보존).

## 6. 메일 발신 도메인 (출시 전 필수에 가까움)

현재 Vercel에 `EMAIL_FROM`이 없어 `onboarding@resend.dev`로 발송된다. Resend는 이 주소에서 **계정 소유자 본인 주소로만** 발송을 허용하므로, 실제 이용자에게는 이메일 인증/비밀번호 재설정 메일이 도착하지 않을 가능성이 높다 (코드는 실패를 로그에만 남기고 사용자에게는 성공처럼 보인다).

- [ ] 도메인 구입 후 Resend → Domains에서 도메인 추가 → DNS(SPF/DKIM) 설정 → Verified 확인
- [ ] Vercel 환경변수 `EMAIL_FROM`을 `K-Coupon Japan <noreply@도메인>`으로 설정 → 재배포
- [ ] 본인 외 다른 주소(Gmail 등)로 비밀번호 재설정 메일이 도착하는지 확인
- 그 전까지 임시 안내: 이메일 가입자가 비밀번호를 잊으면 Google/LINE 로그인을 안내하거나 운영자가 대응한다.

## 7. 법률·사업자 정보 (직접 확인/결정)

코드로 해결된 것이 아니라 **사람이 결정·확인해야 하는 항목**입니다.
